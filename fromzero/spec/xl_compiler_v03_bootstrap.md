## 1. 自举可行性评估

### 1.1 现状盘点

**Rust 编译器雏形 (`xl_compiler\`, v0.1-v0.2)**
- 前端: lexer 只认 ▸↦⟶ / ident / num / = / ( ) / , / `//` 注释;parser 只认 4 类语句
  (`▸x`、`↦y=matmul(x,64)`、`⟶flow(z,32)`、`z=layernorm(y)`)。**无表达式、无变量传值、无控制流、无 IO**。
- 中端: `gate.rs` 做 ▸ 先于 ↦ + 资源预算累加;`ir.rs` 把 7 个算子映射成 XL01 定长字节码。
- 后端: 无(只写 `out.xlbin`,执行靠外部 C VM `xl_vm_train.exe`)。
- 一句话:**它是一个"固定算子序列发射器",不是通用编程语言编译器**。

**自举目标语言 (C# 完整版 `xinglang\Program.cs`, v0.1-v0.16)**
- 三符 ▸↦⟶ + 量纲 ◆ + 量子线路 ⟦⟧ + 控制流(逻辑/比较/⟡/¬)
- 完整算术表达式(+ - * / ^ 括号)、字符串、数组、JSON 寻址、行寻址 §/№/∂
- 变换位置/内禀拍 `:=`、惰性流 ⤳、所有权移动 ⟶!、多参函数、聚合 ∑μ、筛选 ⌿、库引用 ⟚
- 量纲语义已在 C# 实装(`DimOf`):加减不匹配报错、乘除继承/导出、引用继承量纲。

### 1.2 差距清单(当前 → "用星算语写星算语编译器")

写一个编译器,源语言至少要能表达:**词法扫描(循环读字符)、语法分析(递归下降)、符号表(字典)、分支与循环、IO(读源码/写字节)**。逐项对账:

| 能力 | 自举必需度 | Rust 雏形现状 | C# 目标语言现状 |
|---|---|---|---|
| 变量赋值 | 必需 | 仅算子图语句 | ✅ `▸x = expr` |
| 算术表达式 | 必需 | ❌ 本期 v0.3 刚补最小版 | ✅ |
| 符号表/字典 | 必需 | ❌ | ⚠️ 仅平面 Cells,无嵌套结构 |
| 分支(if) | 必需 | ❌ | ⚠️ 仅比较/逻辑,无显式 if |
| 循环 | 必需 | ❌ | ❌ 无(靠内禀拍/流隐式迭代) |
| 函数/抽象 | 必需 | ❌ | ✅ 变换位置/多参函数 |
| 字符串 + 文件 IO | 必需 | ❌ | ✅ v0.5/v0.6 |
| 数组/缓冲 | 必需(token 流) | ❌ | ✅ v0.5 向量 |
| 量纲类型 | 特色(中端肌肉) | ❌ → **本期补** | ✅ v0.10 |
| 错误诊断(行号) | 必需 | ❌ → **本期补** | ✅ |

**诚实结论**:Rust 雏形距自举还差"表达式 → 控制流 → 数据结构 → IO"四座大山。但自举不是一步到位——
**本期先把"中端语义门禁"这块最具星算语特色、又最能训练"在源语言里做静态检查"肌肉的能力焊进编译器本体**。
这正是设计文档第七章路线 `v0.3 量纲类型 → v0.4 惰性流+控制流 → v1.0 自举` 的第一步。

### 1.3 分阶段路线(交付物 + 验收)

- **阶段 1(本期, v0.3)量纲类型系统** —— 已交付
  - 交付: lexer 加 ◆ 与表达式运算符、AST 加 Expr/Define/DimDef、新建 `type_system.rs` 量纲传播 + 带行号报错。
  - 验收: 正确量纲通过;GB+MB 不匹配报 `[第 N 行]`;SAMPLE 字节码 MD5 不变;CI 全绿。
- **阶段 2(v0.4)表达式完备 + 控制流**
  - 交付: 浮点字面量、比较/逻辑、if/loop、变量即值(目前算子图变量无值语义)。
  - 验收: 能在星算语里写出"循环扫 token"这种控制流骨架;量纲检查覆盖到函数/调用。
- **阶段 3(v0.5→v1.0)数据结构 + IO + 自举**
  - 交付: token 缓冲(数组)、字符串/文件 IO、符号表字典;先把 lexer 的扫描逻辑用星算语重写跑通,再逐步吞掉 parser/gate。
  - 验收: 自举版 lexer 与 Rust lexer 输出逐 token 一致 → 同构;最终 `xl_compiler` 由星算语源码编成 XL01 再跑自己。

## 2. 本期推进:为什么选 A(量纲类型)而非 B(构建器)

**选 A。** 理由:
1. **路线点名**:设计文档第七章把"v0.3 量纲类型系统"列为自举第一步;B(构建器)只是把已有"前端→字节码→C VM"胶水串起来,不增加编译器内在能力。
2. **训练自举核心肌肉**:自举编译器必须"在源语言里做静态分析"。量纲检查是中端语义门禁的最小完整闭环(声明→传播→矛盾拦截→带行号诊断),现在用 Rust 把这个闭环焊成模板,将来原样用星算语重写。
3. **可验证**:量纲对错是二值判定,最小可跑、可断言、可回归,不会动既有 17 算子/golden。
4. B 的管线其实已分段可用(各 front 发 xlbin,VM 跑训练),胶水收益低、且 C VM 只认训练 IR 不认任意源码,端到端"任意源码"尚无条件。

## 3. 技术方案(量纲类型系统)

### 3.1 语法扩展(向后兼容)
```
▸ x = expr ◆GB     # 量纲声明:表达式内部量纲自洽 + 记 x=GB
▸ x = expr         # 量纲推断:表达式结果量纲记入 x
```
- 既有 `▸ x`、`↦ y = op(...)`、`z = op(...)`、`⟶ ...` **语法与发射完全不变**。
- lexer 新增 token:`◆`(DimSig)、量纲名(DimName)、`+ - * / ^`;并给每个 token 记**源行号**。

### 3.2 量纲传播规则(镜像 C# `DimOf`)
| 运算 | 规则 |
|---|---|
| 数字字面量 | 无量纲(None) |
| 位置引用 | 继承该位置声明/推断量纲 |
| `+` `-` | 两侧都有量纲且不同 → **编译错**;否则继承有量纲那侧 |
| `*` `/` | 同量纲继承;异量纲 → 导出(None,不追踪复合) |
| `^` | 保留左量纲 |
| 一元 `-` | 量纲不变 |
| 未声明位置 | 编译错(引用了未声明的位置) |

### 3.3 数据流
```
源码 → lexer(带行号) → parser(AST: Expr/Define/DimDef)
     → gate::check(▸顺序+预算, 既有, 不变)
     → type_system::check(量纲传播, 新; 失败→带行号报错→拿不到字节码)
     → ir::emit(Define/DimDef 不落 XL01, 仅编译期注解) → out.xlbin
```

### 3.4 不破坏既有产物的保证
- `ir::emit` 对新语句发射空(无新字节);`gate` 对新语句不计预算。
- 既有 SAMPLE 无 Define/DimDef,走原路径 → `out.xlbin` MD5 保持 `596cf4355075cafdd0cc03c703ac0cda`。

### 3.5 已知边界(诚实)
- 浮点字面量未支持(`.` 仍属标识符字符);本期量纲演示用整数,够用。
- `◆GB` 声明量纲与表达式推断量纲的**交叉校验**未做(C# 也不做);声明量纲以用户为准。
- 算子训练图(matmul 等)的张量量纲未纳入,留 v0.4。
